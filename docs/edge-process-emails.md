# Edge Function - Procesamiento de correos

## Descripción general

`process-emails` es la Edge Function que convierte correos entrantes en tickets de la mesa de ayuda. Soporta dos modos de invocación por HTTP: un modo "webhook" en el que recibe uno o varios correos ya parseados como JSON (`{ emails: [...] }` / `{ messages: [...] }` / un correo suelto), y un modo legado `{ mode: "sync-mailbox" }` que lee directamente el buzón de Outlook (`inbox` o una carpeta configurada) vía Microsoft Graph. Por cada correo válido crea un ticket en Supabase, sube adjuntos e imágenes inline a Supabase Storage, asigna un técnico disponible consultando una lista de SharePoint, y opcionalmente envía notificaciones por correo (al resolutor y, si está habilitado, una respuesta automática al solicitante). Está registrada en `supabase/config.toml` con `verify_jwt = false`.

## Archivos

| Archivo | Rol |
|---|---|
| `config.ts` | Carga variables de entorno hacia `ProcessEmailsConfig`, con valores por defecto para buckets de storage y tamaño máximo de lote. |
| `graph.ts` | Cliente Graph: token OAuth, lectura de mensajes/adjuntos no leídos, marcar como leído, mover de carpeta, envío de respuestas automáticas y notificaciones, lectura/actualización de la lista de usuarios de SharePoint. |
| `html.ts` | Sanitizador de HTML propio (allowlist de tags/atributos vía regex) para el cuerpo del correo, y reemplazo de referencias `cid:` por URLs públicas de Storage. |
| `index.ts` | Entry point: normaliza el payload de entrada (webhook o Graph), orquesta la creación del ticket por mensaje, y expone el modo legado de sincronización de buzón. |
| `resolvers.ts` | Lógica de asignación de técnico: filtra usuarios de SharePoint con `Rol = 'Tecnico'` y `Disponible = 'Disponible'`, elige el de menor carga de casos, e incrementa su contador. |
| `storage.ts` | Sube adjuntos (inline y regulares) a los buckets de Supabase Storage configurados y devuelve URLs públicas. |
| `tickets.ts` | Inserta el ticket en `TBL_Ticket_Solvi`, evita reprocesar el mismo correo (`ticket_solvi_mail_conversation_id`), y guarda la relación de archivos en `TBL_Ticket_Attachments_Solvi`. |
| `types.ts` | Interfaces del módulo: config, payloads entrantes, tipos de Graph, y modelos de ticket/adjunto. |

## Funciones y constantes clave

- **`loadConfig(): ProcessEmailsConfig`** (`config.ts`): variables requeridas `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `AZURE_TENANT_ID`, `SOLVI_CLIENT_ID`, `SOLVI_CLIENT_SECRET`, `SOLVI_MAILBOX_USER`, `SHAREPOINT_SITE_ID`, `SHAREPOINT_USERS_LIST_ID`; opcionales `SOLVI_SOURCE_FOLDER_ID`, `SOLVI_PROCESSED_FOLDER_ID`, `TICKET_ATTACHMENTS_BUCKET` (default `ticket-attachments`), `TICKET_INLINE_BUCKET` (default `ticket-inline`), `SEND_AUTO_REPLY` (booleano, default `false`), `MAX_MESSAGES` (default 40, tope duro de 40 aunque se configure un valor mayor).
- **`getGraphAccessToken`, `listUnreadMessages`, `listMessageAttachments`, `markMessageAsRead`, `moveMessage`** (`graph.ts`): operaciones estándar de Graph sobre el buzón (`isRead eq false`, orden `receivedDateTime asc`, tope `maxMessages`).
- **`sendAutoReply`, `sendCaseCreationReply`, `sendResolverNotification`** (`graph.ts`): tres variantes de correo HTML (respuesta automática al solicitante desde el hilo original vía `createReply`, confirmación de creación de caso, notificación al resolutor asignado vía `sendMail`). Nota: `sendCaseCreationReply` está definida y exportada pero **no se invoca desde `index.ts`** (código muerto).
- **`listSharePointUsers` / `updateSharePointUserFields`** (`graph.ts`): lee/actualiza ítems de la lista de SharePoint de usuarios/técnicos vía Graph (`$expand=fields`).
- **`sanitizeHtml(html)`** (`html.ts`): limpia el HTML del correo con un allowlist de tags (`a, b, br, div, em, i, img, li, ol, p, span, strong, table...`) y atributos (`alt, href, src, target, ...`), quita `<script>`/`<style>`/comentarios, fuerza `target="_blank"`/`rel="noopener noreferrer"` en links, y descarta `<img>` cuyo `src` sea `cid:`/`data:` sin resolver antes.
- **`replaceCidSources(html, inlineFilesByCid)`**: sustituye `src="cid:..."` por la URL pública ya subida a Storage.
- **`resolveTechnician`, `processMessage`, `run`** (`index.ts`): ver flujo abajo.
- **`extractPayloadFromBody` / `extractPayloadListFromBody` / `validateIncomingPayload`**: normalizan distintas formas de payload webhook (`{message: {...}}`, `{emails: [...]}`, `{messages: [...]}`, o el objeto correo directamente) y exigen al menos `subject`, `body`, remitente o adjuntos.
- **`listAvailableTechnicians` / `selectTechnicianWithLowestCases` / `incrementTechnicianCaseCount` / `buildResolverAssignment`** (`resolvers.ts`): filtran técnicos disponibles, seleccionan el de menor `caseCount` (desempate alfabético por nombre, `localeCompare` con `es`), y hacen `PATCH` a SharePoint para incrementar su contador de casos — **sin operación atómica**: se lee `caseCount` y se escribe `caseCount + 1` sin lock, ver hallazgos.
- **`uploadInlineAttachment` / `uploadRegularAttachment`** (`storage.ts`): suben bytes a Supabase Storage (`upsert: true`) bajo `{carpeta}/inline/...` o `{carpeta}/attachments/...`, devolviendo `getPublicUrl`.
- **`findExistingTicketId` / `createTicket` / `saveTicketFiles`** (`tickets.ts`): deduplicación por `ticket_solvi_mail_conversation_id` (usa el `id` del mensaje de Graph, no el `internetMessageId` real de RFC822 pese a que el parámetro se llama así — ver hallazgos), inserción en `TBL_Ticket_Solvi` con SLA fijo de 2 horas (`fechaMaxima = fechaActual + 2h`, hardcodeado, sin relación con el módulo de festivos/horario de `monitor-ticket-expirations`), y relación de adjuntos en `TBL_Ticket_Attachments_Solvi`.
- **Constantes**: `DEFAULT_MAX_MESSAGES = 40`, `DEFAULT_ATTACHMENTS_BUCKET = "ticket-attachments"`, `DEFAULT_INLINE_BUCKET = "ticket-inline"`, `GRAPH_SCOPE`, SLA hardcodeado de 2 horas en `buildTicketPayload` (`tickets.ts`).

## Flujo del módulo

El handler `Deno.serve` distingue tres caminos:

1. **`GET`**: responde una descripción del endpoint (`mode: "http-endpoint"`), útil como *health check*/documentación en vivo.
2. **`POST` con `{ mode: "sync-mailbox" }` (modo legado)**: ejecuta `run()`, que obtiene token de Graph, lista mensajes no leídos del buzón (`listUnreadMessages`) y procesa cada uno con `processMessage(..., syncMailboxState = true)`, que al final marca el mensaje como leído y opcionalmente lo mueve a la carpeta de procesados (`SOLVI_PROCESSED_FOLDER_ID`).
3. **`POST` con payload de correo(s) (modo webhook, camino principal)**: extrae uno o varios `IncomingEmailPayload` del body, valida cada uno, los convierte a la forma interna `GraphMessage`/`GraphAttachment` (`buildMessageFromPayload`, `buildAttachmentsFromPayload`), y llama `processMessage(..., attachments, source, syncMailboxState = false)` — en este camino nunca se toca el buzón real (no hay `markMessageAsRead`/`moveMessage`) porque el mensaje no proviene de Graph.

**`processMessage`** (núcleo compartido de ambos caminos):
1. Deduplicación: `findExistingTicketId` busca un ticket existente por `ticket_solvi_mail_conversation_id` — si existe, retorna `status: "skipped"` sin más efectos.
2. Adjuntos: si no vienen ya resueltos (modo mailbox), los pide a Graph (`listMessageAttachments`); separa inline (`extractInlineAttachments`, imágenes con `contentId`) de regulares (`extractRegularAttachments`).
3. Storage: sube inline y regulares a sus buckets respectivos (`uploadInlineImages`, `uploadRegularAttachments`), generando URLs públicas.
4. HTML: resuelve el cuerpo (HTML nativo, o texto plano convertido con `textToHtml`), reemplaza `cid:` por URLs de Storage (`replaceCidSources`) y sanitiza (`sanitizeHtml`).
5. Asignación de técnico: `resolveTechnician` consulta SharePoint, filtra por rol/disponibilidad y selecciona el de menor carga; si no hay ninguno disponible, lanza error (el mensaje completo falla, no se crea el ticket sin resolutor — pese a que el estado `"pendiente_asignacion"` existe en `buildTicketPayload` para el caso `resolver == null`, ese camino nunca se alcanza porque `resolveTechnician` ya lanzó antes).
6. Persistencia: `createTicket` inserta la fila en `TBL_Ticket_Solvi` (con SLA de 2 horas fijo) y `saveTicketFiles` relaciona los archivos subidos.
7. Efectos "no críticos" (envueltos en `runNonCriticalStep`, que sólo hace `console.warn` si fallan, sin abortar el proceso): incrementar el contador de casos del técnico, notificar por correo al resolutor.
8. Respuesta automática al solicitante: sólo si `SEND_AUTO_REPLY=true`; el fallo se captura y se refleja en `autoReplyStatus`/`autoReplyReason` sin abortar.
9. Sincronización del buzón (sólo modo legado): marca como leído y mueve de carpeta.
10. Errores no capturados dentro de `processMessage` (por ejemplo, fallo de `createTicket` o de `resolveTechnician`) sí abortan ese mensaje puntual — el bucle exterior (`run` o el loop de payloads) los captura por mensaje y continúa con el resto, acumulando en `result.details`/`result.failed`.
11. Respuesta: JSON `ProcessResult` (`processed`, `skipped`, `failed`, `details[]`, `autoReplySummary`), status `200` si `ok`, `207` si hubo fallos parciales, `500` ante error global no controlado.

## Dependencias

- **Deno runtime**: `Deno.env`, `Deno.serve`, `fetch`, `atob`/`Uint8Array` para decodificar adjuntos base64, `crypto.randomUUID()`.
- **`@supabase/supabase-js`**: cliente admin (`service_role`) para Postgres y Storage.
- **Microsoft Graph**: llamadas `fetch` directas (mail, adjuntos, SharePoint list items) — sin SDK, similar a las demás funciones del proyecto.
- **Variables de entorno**: ver lista completa en `loadConfig` arriba.
- **Tipos duplicados con el esquema real**: `types.ts` define `TicketInsertPayload`/`TicketRecord` con campos genéricos (`titulo`, `descripcion`, `correo_solicitante`, `graph_message_id`, `internet_message_id`, `storage_folder`, etc.), pero `tickets.ts::buildTicketPayload` construye y retorna en tiempo de ejecución un objeto con nombres de columna completamente distintos (`ticket_solvi_titulo`, `ticket_solvi_descripcion`, `ticket_solvi_correo_solicitante`, `ticket_solvi_mail_conversation_id`, sin `internet_message_id` ni `storage_folder`), es decir, **el objeto real insertado no cumple la interfaz `TicketInsertPayload` que dice implementar** — ver hallazgos.
- No hay tipos compartidos con `src/Models/*` del frontend; el frontend usa su propio tipo `Ticket` (PascalCase, `src/Models/Tickets.ts`) desconectado de este módulo Deno.

## Oportunidades de mejora

- **Tipo `TicketInsertPayload` desincronizado del código real** (`types.ts` vs `tickets.ts::buildTicketPayload`): la interfaz exige `titulo`, `descripcion`, `correo_solicitante`, `graph_message_id`, `storage_folder`, etc., pero el objeto realmente construido usa el prefijo `ticket_solvi_*` y omite campos como `internet_message_id`/`storage_folder`/`id_resolutor_sharepoint` que si declara la interfaz. Esto indica que el chequeo de tipos de TypeScript no está bloqueando el deploy (Deno Deploy/Supabase Edge Functions puede ejecutar el código igualmente aunque no compile con `tsc --strict`), lo cual es un riesgo: cualquier refactor futuro que confíe en la interfaz declarada trabajará con información falsa sobre la forma real de los datos. Se recomienda corregir la interfaz para reflejar el esquema real de `TBL_Ticket_Solvi` o generar los tipos desde la base de datos.
- **`findExistingTicketId` hace la misma consulta dos veces**: llama a `findTicketIdInTable(supabase, "TBL_Ticket_Solvi", ...)` y, si no encuentra nada, **vuelve a llamar exactamente a la misma función con los mismos argumentos** (`tickets.ts`, líneas ~70-86) en lugar de, por ejemplo, buscar también por `internetMessageId`. Es una consulta redundante a Postgres en cada correo procesado, y sugiere una función incompleta (el parámetro `internetMessageId` de `findTicketIdInTable` nunca se usa realmente para buscar, sólo se comprueba que no sea null antes de retornar `null`).
- **`sendCaseCreationReply` exportada pero nunca usada**: código muerto en `graph.ts` que además duplica casi todo `sendAutoReply` — candidato a eliminar o a consolidar en una sola función parametrizada.
- **Condición redundante en `index.ts`**: `if (config.sendAutoReply) {...} else if (!config.sendAutoReply) {...}` es lógicamente un simple `if/else` (la segunda condición siempre es cierta si se llegó al `else`); no es un bug funcional pero indica falta de limpieza/revisión de código.
- **Incremento de contador de casos sin atomicidad** (`resolvers.ts::incrementTechnicianCaseCount`): se lee `technician.caseCount` (de una consulta previa) y se escribe `caseCount + 1` vía `PATCH` a SharePoint. Si dos correos llegan casi simultáneamente (por ejemplo, dos webhooks concurrentes), ambos pueden leer el mismo `caseCount` y escribir el mismo valor incrementado una sola vez, perdiendo una actualización (*race condition* clásica de "read-modify-write" sin lock) y sesgando la selección del "técnico con menos casos" a futuro.
- **SLA de 2 horas hardcodeado y desconectado del módulo de vencimientos**: `buildTicketPayload` fija `fechaMaxima = fechaApertura + 2 horas` sin considerar horario laboral, fines de semana o festivos (a diferencia de `monitor-ticket-expirations/time.ts`, que sí calcula festivos colombianos). Un ticket creado un viernes a las 16:00 vencería sábado 18:00, fuera de horario laboral, lo cual es inconsistente con las reglas de negocio de la función de monitoreo.
- **Si `resolveTechnician` falla, se pierde el correo completo**: al no haber ningún técnico disponible, `processMessage` lanza una excepción que hace fallar todo el procesamiento del mensaje (columna `status: "failed"` en la respuesta) — el ticket nunca se crea, aunque el estado `"pendiente_asignacion"` existe en el modelo de datos para representar justamente "sin resolutor asignado". Esto puede traducirse en pérdida silenciosa de solicitudes de usuarios si, en un momento dado, ningún técnico figura como `Disponible` en SharePoint (por ejemplo, fuera de horario o por error de datos), ya que el modo webhook no vuelve a reintentar automáticamente ese correo.
- **Falta de reintentos/idempotencia ante fallos parciales**: si `createTicket` tiene éxito pero `saveTicketFiles` falla (excepción no capturada dentro de `processMessage`), el ticket ya quedó creado en Postgres pero sin sus adjuntos relacionados, y el mensaje completo se reporta como `"failed"` — en un reintento posterior (si lo hubiera) `findExistingTicketId` lo detectaría como ya existente y lo saltaría, dejando los adjuntos huérfanos para siempre sin ninguna alerta.
- **Duplicación de la lógica de autenticación Graph**: igual que en los otros módulos, `getGraphAccessToken` se repite casi textual en `monitor-ticket-expirations`, `sync-sharepoint-list`, `obtener-disponibilidad-*`; buen candidato para un módulo `_shared`.
- **Sanitizador de HTML basado en regex propio** (`html.ts`): implementa un allowlist de tags/atributos con expresiones regulares en vez de un parser DOM real (no hay `deno-dom` ni similar). Los sanitizadores basados en regex son notoriamente frágiles ante HTML malformado o vectores de *bypass* (anidamiento raro, atributos con comillas mixtas); para contenido que proviene de remitentes externos no confiables (correos), sería más robusto usar un parser HTML dedicado.
- **Sin límite de tamaño para adjuntos**: no se observa validación de `size` de los adjuntos antes de decodificarlos (`decodeBase64ToUint8Array`) y subirlos a Storage; un correo con adjuntos muy grandes podría agotar memoria/tiempo de la Edge Function sin control.
- **Sin pruebas**: no se encontró cobertura de test para la normalización de payloads (`extractPayloadFromBody`, `buildMessageFromPayload`), la sanitización de HTML, ni la selección de técnico — funciones puras fácilmente testeables mediante unit tests.
