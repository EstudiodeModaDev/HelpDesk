# Edge Function - Monitoreo de vencimiento de tickets

## Descripción general

`monitor-ticket-expirations` es una Edge Function de Supabase (Deno) que revisa periódicamente los tickets abiertos en la tabla `TBL_Ticket_Solvi` para detectar cuáles ya vencieron o están próximos a vencer, y actúa en consecuencia: marca los vencidos como "Fuera de tiempo", registra trazabilidad en `TBL_Seguimientos_Solvi` y envía correos por Microsoft Graph (al resolutor). Según el `README.md` del propio módulo, se dispara mediante un cron de PostgreSQL (`pg_cron` + `net.http_post`) cada 25 minutos; también puede invocarse manualmente por HTTP (`GET`/`POST`). Habla con tres sistemas externos: Microsoft Entra ID (OAuth client-credentials), Microsoft Graph (`sendMail`) y Supabase Postgres (lectura/escritura de tickets y seguimientos).

## Archivos

| Archivo | Rol |
|---|---|
| `config.ts` | Carga y valida variables de entorno (`Deno.env`) hacia un objeto `MonitorConfig`; define umbrales por defecto. |
| `graph.ts` | Cliente Graph ad-hoc: obtiene token OAuth client-credentials, envía correos (`sendMail`), y arma el HTML de los dos tipos de correo (vencido / próximo a vencer). |
| `index.ts` | Entry point (`Deno.serve`): orquesta el flujo completo — validación de horario/festivo, paginación de tickets, clasificación (vencido/alerta/omitido) y ejecución de acciones. |
| `tickets.ts` | Acceso a datos vía `@supabase/supabase-js`: cliente admin, consulta paginada de tickets abiertos, actualización de estado, inserción de seguimientos, chequeo de duplicados. |
| `time.ts` | Utilidades de tiempo: hora actual en Colombia (offset fijo `-05:00`), cálculo de festivos colombianos (fijos, Ley Emiliani, móviles desde Pascua), y helpers de horario laboral. |
| `types.ts` | Interfaces compartidas del módulo (`MonitorConfig`, `Ticket`, `Tracking`, `ExecutionSummary`, tipos de respuesta de Graph). |

## Funciones y constantes clave

- **`loadConfig(): MonitorConfig`** (`config.ts`): lee variables requeridas (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `AZURE_TENANT_ID`, `SOLVI_CLIENT_ID`, `SOLVI_CLIENT_SECRET`, `SOLVI_MAILBOX_USER`) y opcionales (`TICKET_WARNING_THRESHOLD_HOURS`, default 4; `TICKET_MONITOR_PAGE_SIZE`, default 200). Lanza excepción si falta alguna requerida. Incluye `getFirstAvailableEnv` (busca la primera de una lista de variables) pero **no se usa** en `loadConfig` — ver hallazgos.
- **`getGraphAccessToken(config)`** (`graph.ts`): `POST` a `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token` con `grant_type=client_credentials`. Retorna el `access_token`. Efecto secundario: llamada HTTP externa a Azure AD.
- **`sendGraphMail` / `sendExpirationEmail` / `sendWarningEmail`** (`graph.ts`): construyen HTML (con escape básico) y llaman `POST /users/{mailbox}/sendMail` de Graph v1.0. Requieren `ticket.ticket_solvi_correo_resolutor`; si falta, lanzan error.
- **`fetchOpenTicketsPage(supabase, pageSize, from)`** (`tickets.ts`): consulta `TBL_Ticket_Solvi` filtrando `ticket_solvi_estado in ('En Atención','En Atencion')`, excluyendo `ticket_solvi_resolutor = 'Automatizaciones'` y con `ticket_solvi_fechamaxima` no nulo, paginada con `.range(from, to)`.
- **`updateTicketStatus(supabase, ticketId, status)`**: `UPDATE` de `ticket_solvi_estado` por `ticket_solvi_id`.
- **`createTracking` / `buildExpiredTracking` / `buildWarningTracking`**: insertan filas en `TBL_Seguimientos_Solvi` con tipo de acción `EXPIRED_TRACKING_TYPE` ("Cambio automático a Fuera de tiempo") o `WARNING_TRACKING_TYPE` ("Alerta automática de vencimiento"). `buildWarningTracking` existe pero, como se detalla abajo, **no se invoca desde `index.ts`**.
- **`hasTrackingEvent(supabase, ticketId, trackingType)`**: consulta si ya existe un seguimiento de un tipo dado para el ticket — pensada como mecanismo antiduplicados, pero **no se llama desde ningún punto de `index.ts`**.
- **`getCurrentColombiaTime(date)` / `isWeekend` / `isHoliday` / `isBusinessHours`** (`time.ts`): calculan la hora local de Bogotá (offset fijo `-05:00`, sin usar `Intl`/zona horaria real, por lo que no ajusta automáticamente ante cambios de reglas de DST — Colombia no tiene DST actualmente, pero el cálculo es manual). `isBusinessHours` usa ventana fija `07:00–17:00`. `isHoliday` calcula festivos colombianos en tiempo real (fijos + Emiliani + móviles desde Pascua) sin depender de una API externa.
- **`run(): Promise<ExecutionSummary>`** (`index.ts`): función principal; corta temprano si es fin de semana, festivo o fuera de horario laboral (no procesa nada en esos casos). Si corresponde procesar, pagina tickets con `fetchOpenTicketsPage`, y por cada ticket calcula `hoursRemaining` y decide entre `processExpiredTicket`, `processWarningTicket` o marcarlo como `skipped`.
- **`processExpiredTicket`**: actualiza estado a `"Fuera de tiempo"`, crea tracking de tipo `EXPIRED_TRACKING_TYPE`, y envía `sendExpirationEmail`. Efectos secundarios: 1 UPDATE + 1 INSERT en Supabase + 1 envío de correo por ticket.
- **`processWarningTicket`**: sólo envía `sendWarningEmail`; **no actualiza estado ni crea tracking** (ver hallazgos sobre duplicados).
- **Constantes**: `DEFAULT_WARNING_THRESHOLD_HOURS = 4`, `DEFAULT_PAGE_SIZE = 200`, `GRAPH_SCOPE = "https://graph.microsoft.com/.default"`, `EXPIRED_STATUS = "Fuera de tiempo"`, umbral de horario laboral `07:00–17:00`.

## Flujo del módulo

1. **Disparo**: cron de PostgreSQL cada 25 minutos (`select cron.schedule('monitor-ticket-expirations', '*/25 * * * *', ...)` documentado en el `README.md` del módulo, vía `net.http_post` con `Authorization: Bearer <service_role_key>`); también admite invocación manual `GET`/`POST` sobre el endpoint HTTP de la función.
2. `Deno.serve` valida el método (`405` si no es `GET`/`POST`) y llama a `run()`.
3. `run()` calcula la hora de Colombia y corta inmediatamente (retorna un resumen vacío con `reason`) si es fin de semana, festivo nacional o fuera de la ventana `07:00–17:00` — evita llamadas innecesarias a Graph/Supabase fuera de horario laboral.
4. Si corresponde procesar: `loadConfig()` valida env vars, se crea el cliente admin de Supabase (`service_role`, sin persistencia de sesión) y se obtiene un token de Graph (`client_credentials`).
5. Se paginan los tickets abiertos (`fetchOpenTicketsPage`) en lotes de `pageSize` (200 por defecto) hasta agotar resultados.
6. Por cada ticket: se parsea `ticket_solvi_fechamaxima` (asumiendo zona `-05:00` si no trae offset); si ya venció (`now > dueDate`) se ejecuta el flujo de "vencido" (cambio de estado + tracking + correo); si faltan menos de `warningThresholdHours` (4h) se envía el correo de alerta; en cualquier otro caso se cuenta como `skipped`.
7. Los errores por ticket individual se capturan (`try/catch` dentro del loop) y se acumulan en `summary.errors` sin abortar el resto del lote — el resto de tickets se sigue procesando.
8. Al finalizar, se retorna un JSON `ExecutionSummary` (`processed`, `expired`, `warningsSent`, `skipped`, `errors`), con status `200` si no hubo errores o `207` (Multi-Status) si los hubo. Un error no controlado en `run()` responde `500` con `reason: "UNHANDLED_ERROR"`.
9. Logging: `console.log` estructurado con etiquetas (`[START]`, `[WEEKEND]`, `[HOLIDAY]`, `[OUT_OF_BUSINESS_HOURS]`, `[TICKET_EXPIRED]`, `[TRACKING_CREATED]`, `[EMAIL_SENT]`, `[TICKET_WARNING]`, `[END]`) y `console.error` para fallos por ticket y fallos globales.

## Dependencias

- **Deno std / runtime**: `Deno.env`, `Deno.serve`, `fetch` nativo; import de `@supabase/functions-js/edge-runtime.d.ts` para tipos del entorno Edge.
- **`@supabase/supabase-js`**: cliente Postgres/Auth para `createClient`.
- **Microsoft Graph**: `fetch` directo a `login.microsoftonline.com` y `graph.microsoft.com/v1.0`, sin SDK.
- **Variables de entorno**: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `AZURE_TENANT_ID`, `SOLVI_CLIENT_ID` (con soporte no usado para `AZURE_CLIENT_ID` como alias, ver hallazgos), `SOLVI_CLIENT_SECRET`, `SOLVI_MAILBOX_USER`, `TICKET_WARNING_THRESHOLD_HOURS` (opcional), `TICKET_MONITOR_PAGE_SIZE` (opcional).
- **Tipos compartidos**: `types.ts` define `Ticket` con campos `ticket_solvi_*` que reflejan literalmente el esquema de la tabla Postgres `TBL_Ticket_Solvi`; el frontend tiene su propio tipo `Ticket` en `src/Models/Tickets.ts` con nombres de campo completamente distintos (`ID`, `Nombreresolutor`, `FechaMaxima`, etc., estilo PascalCase orientado a SharePoint). No hay tipo compartido ni generación automática entre ambos — es duplicación de modelo de dominio bajo dos convenciones de nombres distintas, propensa a desincronizarse si cambia el esquema de la tabla.

## Oportunidades de mejora

- **Bug de duplicados en las alertas de vencimiento próximo**: el propio `README.md` del módulo documenta que la función usa `TBL_Seguimientos_Solvi` para "evitar enviar múltiples alertas del mismo ticket en ejecuciones sucesivas", y `tickets.ts` exporta `hasTrackingEvent` y `buildWarningTracking` para ese propósito. Sin embargo, `processWarningTicket` en `index.ts` **no llama a `hasTrackingEvent` antes de enviar el correo, ni a `createTracking`/`buildWarningTracking` después**. Como el ticket permanece en estado `"En Atención"` mientras está en la ventana de alerta (4 horas) y el cron corre cada 25 minutos, un mismo ticket puede generar hasta ~9 correos de alerta duplicados al mismo resolutor antes de vencer. Esto contradice la documentación del propio módulo y es el hallazgo más concreto y accionable: agregar el chequeo `hasTrackingEvent(..., WARNING_TRACKING_TYPE)` antes de enviar, y `createTracking(buildWarningTracking(...))` después de enviar con éxito.
- **`getFirstAvailableEnv` sin usar**: `config.ts` define esta función y el `README.md` afirma que "si `AZURE_CLIENT_ID` no existe todavía, la función también acepta `SOLVI_CLIENT_ID`", pero `loadConfig()` llama directamente `getRequiredEnv("SOLVI_CLIENT_ID")`, sin pasar por `getFirstAvailableEnv([...])`. La compatibilidad descrita en la documentación no está implementada; si en producción sólo existe `AZURE_CLIENT_ID` (como sugiere el nombre "real" del secreto en Azure), la función fallaría al arrancar.
- **Falta de reintentos ante fallos de Graph**: si `sendGraphMail` falla (por ejemplo, throttling 429 de Graph), el error se captura por ticket individual y se agrega a `summary.errors`, pero no hay backoff/retry; en el caso de tickets vencidos, el estado ya se actualizó a `"Fuera de tiempo"` **antes** de intentar enviar el correo (`processExpiredTicket` llama `updateTicketStatus` y `createTracking` antes de `sendExpirationEmail`), por lo que un fallo de envío deja el ticket marcado como vencido sin que el correo haya salido, y en la siguiente ejecución el ticket ya no será reconsiderado (no matchea el filtro `En Atención`/`En Atencion`) — el correo de vencimiento simplemente nunca se reintenta ni se registra como pendiente.
- **Sin idempotencia ante ejecuciones solapadas**: si el cron dispara una nueva invocación antes de que termine la anterior (por ejemplo, si Graph responde lento), no hay ningún lock/mutex — dos ejecuciones concurrentes podrían procesar el mismo ticket dos veces (aunque el caso de vencidos se autolimita por el cambio de estado, el de alertas no, agravando el punto anterior).
- **Parseo de fechas con supuestos frágiles**: `parseTicketDueDate` en `index.ts` asume timezone `-05:00` si `ticket_solvi_fechamaxima` no trae offset ni "T" (agrega `T00:00:00-05:00`), lo cual puede producir vencimientos incorrectos si el dato se guarda alguna vez en otro formato o con hora sin fecha.
- **Duplicación de lógica de autenticación con Graph**: `getGraphAccessToken` en este módulo es prácticamente idéntica a la de `process-emails/graph.ts`, `sync-sharepoint-list/index.ts` y las funciones `obtener-disponibilidad-*` (mismo endpoint, mismo `client_credentials`, mismo parseo de respuesta). Es un candidato claro para extraer a un módulo compartido (por ejemplo `supabase/functions/_shared/graph-auth.ts`), reduciendo el riesgo de que una corrección de seguridad o de manejo de errores se aplique en una función y se olvide en las demás.
- **Sin límite de tiempo de ejecución considerado para lotes grandes**: el loop de paginación (`while (true)`) procesa todos los tickets abiertos en una sola invocación, enviando correos secuencialmente (`await` uno por uno). Si el volumen de tickets "En Atención" crece significativamente, la función podría acercarse al límite de tiempo de ejecución de las Edge Functions de Supabase (por defecto en el orden de segundos a minutos según plan), dejando tickets sin procesar hasta el siguiente ciclo de cron sin ninguna señal explícita de "se agotó el tiempo".
- **Sin pruebas automatizadas**: no se encontraron archivos de test para el cálculo de festivos/horario (`time.ts`, lógica no trivial con Ley Emiliani y Pascua) ni para la clasificación vencido/alerta/omitido en `index.ts`, pese a ser lógica de negocio con reglas de fecha propensas a errores de borde (medianoche, cambio de año, festivos móviles).
