# Componentes Compartidos / UI genérica

## Descripción general
Este grupo reúne piezas de UI reutilizables sin lógica de dominio propia: un diálogo de confirmación global (`ConfirmProvider`), un interruptor booleano (`Toggle`), un truncador de texto con tooltip (`Trunc`), un renderizador de HTML sanitizado con lightbox de imágenes (`Renderizador`), un editor de texto enriquecido basado en `contentEditable` (`RichTextBase64`) y un formulario que usa ese editor para crear plantillas de contenido (`NuevaPlantilla`). Se usan como bloques de construcción en varias pantallas de tickets, tareas y contenido.

## Archivos
- `src/components/ModalDelete/ConfirmProvider.tsx` (`ConfirmProvider`, `useConfirm`): proveedor de contexto que expone `confirm(opts): Promise<boolean>` y renderiza un diálogo modal de confirmación genérico (título, mensaje, botones aceptar/cancelar, variante destructiva).
- `src/components/Toggle/Toggle.tsx` (`Toggle`): checkbox estilizado como interruptor, controlado 100% por props (`checked`, `onChange`, `label`).
- `src/components/Trunc/trunc.tsx` (`Trunc`): `<span>` que trunca un texto a `maxLenght` caracteres y expone el texto completo vía `data-full`/`aria-label`/tooltip CSS.
- `src/components/Renderizador/Renderizador.tsx` (`HtmlContent`, exportado por defecto): renderiza HTML sanitizado con `DOMPurify` dentro de un `dangerouslySetInnerHTML`, con soporte de lightbox al hacer clic en imágenes.
- `src/components/RichTextBase64/RichTextBase64.tsx` (`RichTextBase64`): editor WYSIWYG minimalista (`contentEditable` + `document.execCommand`) con toolbar (negrita, cursiva, subrayado, listas, enlace, imagen) y subida de imágenes pegadas/arrastradas/insertadas a Supabase.
- `src/components/NuevaPlantilla/NuevaPlantilla.tsx` (`CrearPlantilla`): formulario de alta de plantilla de contenido que usa `RichTextBase64` como campo de cuerpo HTML.

## Flujo del módulo
- **`ConfirmProvider`** se monta una única vez cerca de la raíz (`src/main.tsx`) envolviendo toda la aplicación; cualquier componente descendiente llama `useConfirm()` y usa `await confirm({...})` para bloquear el flujo hasta que el usuario decida. Se encontraron 2 consumidores directos en `src/components`: `Usuarios/Usuarios.tsx` y `Tareas/TareasRegistradas/TareasRegistradas.tsx` (además del propio `main.tsx` que lo instala).
- **`Toggle`** se usa en al menos `Documentar/ActaEntrega/InformacionCaso/InfoActa.tsx` como interruptor de un campo del acta.
- **`Trunc`** se usa en `DetallesTickets/CaseInfoGrid.tsx` y `DetallesTickets/CaseAttachments.tsx` para no romper el layout de la grilla de detalle de ticket con textos largos (nombres de archivo, valores de campo), mostrando el valor completo en el `aria-label`/tooltip.
- **`Renderizador` (`HtmlContent`)** se usa en `DetallesTickets/CaseInfoGrid.tsx` y `Seguimiento/Seguimiento.tsx` para pintar el HTML de comentarios/seguimientos guardado en SharePoint (probablemente generado por `RichTextBase64`), con clic-para-ampliar en las imágenes incrustadas.
- **`RichTextBase64`** se reutiliza como campo de edición de contenido enriquecido en `NuevoTicket/NuevoTicketForm.tsx`, `Documentar/Documentar.tsx`, `NuevoTicketUsuario/NuevoTicketFormUsuario.tsx` y `NuevaPlantilla/NuevaPlantilla.tsx` — es decir, en todos los formularios donde el usuario redacta la descripción de un ticket, un comentario de cierre o una plantilla. El HTML que produce típicamente se guarda tal cual y luego se muestra con `Renderizador`/`HtmlContent` en otra pantalla.
- **`NuevaPlantilla`** es un caso de uso concreto de `RichTextBase64`: el usuario nombra la plantilla, redacta el cuerpo en el editor enriquecido y al enviar el formulario se llama `createPlantilla()`, que persiste `state.Titulo`/`state.HTLM` vía `usePlantillas`.

## Dependencias
- **Funcionalidades**: `content/Plantillas.ts` (`usePlantillas`), `shared/UploadFileToSupabase.ts` (`uploadImageToSupabase`, también usado por `Funcionalidades/Tickets/Documentar.ts` y `Funcionalidades/Tickets/NuevoTicket.ts`).
- **Servicios**: `src/Services/Plantillas.service.ts` (`PlantillasService`), inyectado vía `useGraphServices()`.
- **Librerías externas**: `dompurify` (única aparición de sanitización HTML en el proyecto, en `Renderizador.tsx`), `react-dom` (`createPortal` para el lightbox), `react-hot-toast` (mensajes de error de subida en `RichTextBase64.tsx`), API nativa del navegador `document.execCommand` (deprecada) para el editor enriquecido.

## Oportunidades de mejora
1. **Riesgo de XSS fuera de `Renderizador`**: `Renderizador.tsx` sí sanitiza correctamente con `DOMPurify.sanitize` (con `ALLOWED_URI_REGEXP` restringido a `https/mailto/tel/data:image` y `USE_PROFILES: {html:true}`) antes de usar `dangerouslySetInnerHTML`. Sin embargo, `src/components/Formatos/Formatos.tsx` usa `dangerouslySetInnerHTML={{ __html: TYC_BY_OPCION[opcion] }}` con contenido de una constante local (`TYC_BY_OPCION`) **sin pasar por `DOMPurify`**; aunque hoy el contenido es estático y de confianza, es una segunda vía de `dangerouslySetInnerHTML` en el proyecto que no reutiliza el componente `HtmlContent`/`Renderizador` ya existente, rompiendo la garantía de "todo HTML se sanitiza en un solo punto". Se recomienda encauzar ese contenido también por `Renderizador` o al menos por `DOMPurify.sanitize`.
2. **`document.execCommand` deprecado**: `RichTextBase64.tsx` construye todo su toolbar (negrita, cursiva, listas, enlace, limpiar formato) sobre `document.execCommand`, API marcada como obsoleta en los estándares web y con soporte inconsistente entre navegadores; a mediano plazo convendría migrar a una librería de edición enriquecida mantenida (p. ej. TipTap/Slate) o a un enfoque basado en `Selection`/`Range` propio.
3. **`prompt()` nativo para insertar enlaces**: dentro de `RichTextBase64.tsx`, el botón de "Enlace" usa `window.prompt("URL del enlace:")`, una UX poco cuidada e inconsistente con el resto de modales de la app (que usan diálogos propios como `ConfirmProvider`).
4. **HTML de imagen construido por concatenación de strings**: `buildImgHTML` arma manualmente una cadena `<img src="${src}" ... style="...">` interpolando `src` sin escapar; como `src` viene de `uploadImageToSupabase` (URL propia), el riesgo práctico es bajo, pero es un patrón fráil: cualquier cambio para aceptar `src` de otro origen reintroduciría riesgo de inyección HTML antes de pasar por `DOMPurify` en el punto de lectura.
5. **Nombre de prop con typo**: `Trunc` usa `maxLenght` en vez de `maxLength`, inconsistente con la convención estándar de React/HTML (`maxLength`) y con el resto de la base de código.
6. **Estilos inline extensos en `Renderizador.tsx`**: el `Lightbox` define `overlayStyle`, `contentStyle`, `imgStyle`, `closeBtnStyle` como objetos de estilo inline en el propio archivo `.tsx` en vez de usar una hoja CSS como el resto de componentes del proyecto (todos los demás importan un `.css` dedicado); rompe la convención y dificulta el theming.
7. **Sin manejo de error de carga en `ConfirmProvider`**: `useConfirm` lanza una excepción (`throw new Error(...)`) si se usa fuera del `Provider`, lo cual es correcto, pero no hay ningún fallback visual si `main.tsx` alguna vez deja de envolver un subárbol de rutas (p. ej. rutas cargadas de forma diferida fuera del árbol principal).
8. **Posible pérdida de foco/cursor en `RichTextBase64`**: el `useEffect` que sincroniza `value` externo con `el.innerHTML` reemplaza todo el contenido del editor si difiere, lo que puede mover el cursor al inicio/perder la posición de edición si el componente padre re-renderiza y pasa un `value` recalculado (por ejemplo, tras cada `setField`) — no se observa un guard adicional más allá de la comparación de igualdad de strings.
9. **Alcance de reutilización desigual**: `ConfirmProvider`/`Toggle`/`Trunc`/`Renderizador` tienen relativamente pocos puntos de uso (2 cada uno aparte de la instalación raíz), mientras `RichTextBase64` es el componente compartido con más reuso (4 formularios). Esto sugiere que vale la pena invertir primero en robustecer `RichTextBase64` (tests, manejo de errores de subida, accesibilidad del toolbar) antes que en los demás, dado su mayor radio de impacto.
