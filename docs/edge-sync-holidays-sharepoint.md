# Edge Functions - Sincronización de festivos y listas SharePoint

## Descripción general

Este módulo agrupa dos Edge Functions de sincronización unidireccional hacia Supabase Postgres: `sync-holidays`, que refresca la tabla de festivos colombianos desde una API externa (`festivos.com.co`), y `sync-sharepoint-list`, una función **genérica y configurable** que replica cualquier lista de SharePoint (por defecto, la de resolutores/técnicos) hacia cualquier tabla de Supabase, mapeando campos mediante configuración por variables de entorno o por el body de la petición. Ambas se invocan por HTTP (`GET`/`POST`); no se encontró configuración de cron para ninguna de las dos ni entradas en `supabase/config.toml` (a diferencia de `process-emails`, `sync-sharepoint-list`, `obtener-disponibilidad-*`, que sí están registradas allí — ver hallazgos). Hablan con Microsoft Graph (sólo `sync-sharepoint-list`) y con Supabase Postgres (ambas), además de la API pública de festivos (sólo `sync-holidays`).

## Archivos

| Archivo | Rol |
|---|---|
| `sync-holidays/config.ts` | Carga configuración desde entorno: API key/URL de festivos, credenciales de Supabase, nombre de tabla destino. |
| `sync-holidays/index.ts` | Entry point: descarga festivos de un año desde la API externa y reemplaza por completo el contenido de la tabla destino. |
| `sync-sharepoint-list/config.ts` | Carga configuración extensa y parametrizable (mapeo de campos, valores estáticos, claves de sincronización, tamaños de lote) con validaciones estrictas; expone `mergeConfig` para sobrescribir la config base con parámetros de una petición HTTP puntual. |
| `sync-sharepoint-list/index.ts` | Entry point: resuelve sitio/lista de SharePoint, pagina todos los ítems, los mapea a filas de Supabase según el `syncFieldMap`, hace *upsert* por lotes y, opcionalmente, elimina (*prune*) filas que ya no existen en SharePoint. |

## Funciones y constantes clave

### `sync-holidays`
- **`loadConfig(): SyncHolidaysConfig`**: requiere `FESTIVOS_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL`; opcionales `FESTIVOS_API_URL` (default `https://www.festivos.com.co/api/v1/festivos`) y `HOLIDAYS_TABLE` (default `TBL_Festivos_Solvi`).
- **`resolveYear(request)`**: toma `?year=` de la query string, valida rango `2000–3000`, o usa el año actual (UTC) por defecto.
- **`fetchHolidays(year, apiUrl, apiKey)`**: `GET {apiUrl}?year={year}` con `Authorization: Bearer {apiKey}`; filtra filas incompletas de la respuesta y las mapea a `{ fecha_festivo, dia_semana, nombre_festivo, source_year }`.
- **`replaceHolidays(rows)`**: **efecto secundario destructivo** — hace `DELETE` de *toda* la tabla (`.gte("source_year", 0)`, es decir, todas las filas con `source_year >= 0`) y luego `INSERT` de las filas nuevas. No es un *upsert*; es un reemplazo completo, y no está limitado al año solicitado (borra festivos de *todos* los años ya cargados, no sólo el año consultado).
- **Handler `Deno.serve`**: si la API externa devuelve 0 filas, responde `422` **sin tocar la tabla** (salvaguarda explícita para no vaciarla accidentalmente); si hay filas, ejecuta el reemplazo y responde `200` con conteos.

### `sync-sharepoint-list`
- **Constantes de configuración por defecto**: `DEFAULT_PAGE_SIZE = 200`, `DEFAULT_UPSERT_BATCH_SIZE = 500`, `DEFAULT_DELETE_BATCH_SIZE = 500`, `DEFAULT_TABLE_NAME = "TBL_Resolutor_Solvi"`, `DEFAULT_TARGET_KEY = "sharepoint_id"`, `DEFAULT_SOURCE_KEY = "Id"`, `DEFAULT_FIELD_MAP = { Title: "resolutor_nombre", Correo: "resolutor_correo", Id: "sharepoint_id" }`, `DEFAULT_STATIC_VALUES = { resolutor_estado: "Activo" }`.
- **`loadConfig()` / `mergeConfig(base, input)`** (`config.ts`): construyen `SyncSharePointListConfig`; validan que exista `sharePointListId` o `sharePointListName`, y `sharePointSiteId` o (`sharePointSiteHostname` + `sharePointSitePath`); parsean `SHAREPOINT_SYNC_FIELD_MAP`/`SHAREPOINT_SYNC_STATIC_VALUES` como JSON con validación estricta de forma. `mergeConfig` permite que una petición HTTP puntual sobrescriba casi cualquier parámetro (lista, sitio, tamaños de lote, mapeo de campos) sin redeploy.
- **`getGraphAccessToken`, `graphFetch`, `resolveSiteId`, `resolveListId`, `fetchSharePointItems`** (`index.ts`): autenticación `client_credentials`, resolución de sitio/lista por nombre o ID, y paginación completa de los ítems de la lista (`$expand=fields($select=...)`, siguiendo `@odata.nextLink`).
- **`mapItemToRow(item, config)`**: construye la fila destino aplicando `syncTargetKey` (desde `syncSourceKey`, con soporte especial para el campo `Id` de SharePoint → `item.id`), el `syncFieldMap` (campo SharePoint → columna Supabase) y los `syncStaticValues` (constantes fijas, ej. `resolutor_estado: "Activo"`); si `syncUseResolverActivoRule` está activo (default `true`), calcula `resolutor_activo = !shouldSetResolverActivoFalse(fields)` en base al campo `Disponible` de SharePoint (`"no disponible"` o `"inactivo"` → `false`).
- **`upsertRows(config, rows)`**: hace *upsert* (`onConflict: syncTargetKey`) en lotes de `upsertBatchSize` (500 por defecto).
- **`pruneMissingRows(config, sourceRows)`**: sólo si `syncPruneMissing = true` (default `false`); trae *todas* las claves existentes en la tabla destino, calcula la diferencia contra las claves recién sincronizadas, y elimina en lotes (`syncDeleteBatchSize`) las que ya no están en SharePoint.
- **`readRequestBody(request)`**: parsea y valida exhaustivamente cada campo opcional del body `POST` (tipo correcto, no vacío, enteros positivos) antes de pasarlo a `mergeConfig` — es la validación de entrada más estricta observada entre las funciones del proyecto.
- **`isSharePointIdField(value)`**: trata el nombre de campo `"id"` (case-insensitive) como especial, mapeándolo a `item.id` (el GUID de Graph) en vez de buscarlo dentro de `item.fields`.

## Flujo del módulo

### `sync-holidays`
1. Invocación HTTP `GET`/`POST` (sin evidencia de cron ni entrada en `config.toml`; presumiblemente se agenda externamente o se dispara manualmente al inicio de cada año).
2. Valida método, resuelve el año (`?year=`), llama a la API pública de festivos con la API key.
3. Si hay filas, `replaceHolidays` borra toda la tabla y reinserta — operación atómica sólo en el sentido de "una función de invocación", pero **no transaccional** (el `DELETE` y el `INSERT` son dos operaciones separadas contra PostgREST; un fallo entre medio deja la tabla vacía).
4. Responde `200` con `{ ok, year, fetched, inserted, message }`, `422` si la API no devolvió festivos, o `500` ante cualquier excepción (incluida la del `DELETE`/`INSERT`).
5. Logging: sólo `console.error` en el `catch` final; no hay logs de progreso (cuántas filas se borraron/insertaron) más allá de la respuesta HTTP.

### `sync-sharepoint-list`
1. Invocación HTTP `GET`/`POST` (registrada en `supabase/config.toml` con `verify_jwt = false`; tampoco hay evidencia de cron, por lo que probablemente se agenda vía `pg_cron`+`net.http_post` externamente, igual que `monitor-ticket-expirations`, o se dispara manualmente).
2. `loadConfig()` construye la configuración base desde variables de entorno; `readRequestBody` parsea overrides opcionales del body `POST`; `mergeConfig` produce la configuración final y revalida las combinaciones requeridas (lista/sitio).
3. Autenticación Graph (`client_credentials`), resolución de `siteId` (por ID directo o por `hostname:path`) y `listId` (por ID directo o buscando por `displayName`).
4. `fetchSharePointItems` pagina *todos* los ítems de la lista, seleccionando sólo los campos declarados en `syncFieldMap` (optimiza el payload de Graph).
5. Si no hay ítems, responde `200` sin tocar Supabase (mensaje explícito de que no se modificó nada).
6. Si hay ítems, `mapItemToRow` transforma cada uno; `upsertRows` los graba por lotes; `pruneMissingRows` opcionalmente borra los que ya no existen en origen.
7. Responde `200` con `{ ok, fetched, upserted, deleted, listId, table }`, o `500` con el mensaje de error ante cualquier fallo (autenticación, Graph, o Postgres) — un fallo a mitad de la paginación o del *upsert* por lotes deja el estado parcialmente sincronizado sin ninguna marca de qué lote falló.
8. Logging: `console.error("sync-sharepoint-list execution failed", { error: reason })` únicamente en el catch final; sin logs de progreso por página/lote.

## Dependencias

- **Deno runtime**: `Deno.env`, `Deno.serve`, `fetch`, `URLSearchParams`, `JSON.parse`.
- **`@supabase/supabase-js`**: cliente `service_role` para `delete`/`insert` (`sync-holidays`) y `upsert`/`select`/`delete` (`sync-sharepoint-list`).
- **Microsoft Graph**: sólo en `sync-sharepoint-list`, vía `fetch` directo (sin SDK), igual que el resto de funciones del proyecto.
- **API externa de terceros**: `sync-holidays` depende de `festivos.com.co` (o la URL configurada en `FESTIVOS_API_URL`), un servicio externo fuera del control del equipo — contraste directo con `monitor-ticket-expirations/time.ts`, que calcula los mismos festivos colombianos de forma local sin depender de ninguna API (duplicación de fuente de verdad: dos formas distintas de determinar festivos colombianos conviven en el monorepo, ver hallazgos).
- **Variables de entorno `sync-holidays`**: `FESTIVOS_API_KEY`, `FESTIVOS_API_URL` (opcional), `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL`, `HOLIDAYS_TABLE` (opcional).
- **Variables de entorno `sync-sharepoint-list`**: `AZURE_TENANT_ID`, `SHAREPOINT_CLIENT_ID`/`SOLVI_CLIENT_ID` (fallback), `SHAREPOINT_CLIENT_SECRET`/`SOLVI_CLIENT_SECRET` (fallback), `SHAREPOINT_GRAPH_SCOPE` (opcional), `SHAREPOINT_LIST_ID`/`SHAREPOINT_SYNC_LIST_NAME`, `SHAREPOINT_SITE_ID` o `SHAREPOINT_SITE_HOSTNAME`+`SHAREPOINT_SITE_PATH`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL`, y una decena de variables `SHAREPOINT_SYNC_*` opcionales (tamaños de lote, mapeo de campos JSON, valores estáticos JSON, flags booleanos).
- **Tipos duplicados**: ambas funciones definen sus propios tipos locales de Graph (`GraphTokenResponse`, `GraphListResponse<T>`) de forma independiente entre sí y respecto de las demás Edge Functions del repo — no hay un módulo `_shared`.

## Oportunidades de mejora

- **`sync-holidays` no filtra por año al borrar**: `replaceHolidays` ejecuta `DELETE ... WHERE source_year >= 0`, es decir, **borra los festivos de todos los años previamente cargados**, no sólo del año consultado (`?year=`). Si el objetivo es sincronizar un año específico (por ejemplo, para precargar el año siguiente sin perder el actual), el comportamiento real es destructivo para toda la tabla. Esto también contradice el nombre semántico de la operación ("sync" sugiere fusión, no reemplazo total); conviene documentar explícitamente esta semántica de "full replace" o cambiarla a un `upsert` filtrado por `source_year`.
- **Operación no transaccional (`DELETE` + `INSERT` separados)**: si el `INSERT` posterior al `DELETE` falla (por ejemplo, error de red o violación de constraint), la tabla de festivos queda **vacía**, lo cual tiene impacto directo en `monitor-ticket-expirations` (que usaría festivos, si consultara esta tabla) — aunque, como se documenta en el módulo 2, `monitor-ticket-expirations/time.ts` en realidad calcula festivos localmente y no lee esta tabla, por lo que hoy el radio de impacto real de este bug es menor de lo que parece a primera vista, pero sugiere una tabla cuyo propósito real (¿la consume otro consumidor no incluido en este análisis?) no está del todo claro.
- **Duplicación de fuente de verdad de festivos colombianos**: existen dos implementaciones independientes — el cálculo local en `monitor-ticket-expirations/time.ts` (fijos + Ley Emiliani + Pascua) y la sincronización desde una API externa de pago/terceros en `sync-holidays`. Si alguna vez `monitor-ticket-expirations` migrara a leer de `TBL_Festivos_Solvi` en lugar de calcular localmente (o viceversa), ambas fuentes podrían divergir (por ejemplo, ante un festivo trasladado por decreto especial que sólo una de las dos fuentes contemple). Vale la pena decidir una única fuente de verdad.
- **`sync-sharepoint-list` no está en `supabase/config.toml` junto a las demás para `sync-holidays`**: `supabase/config.toml` registra explícitamente `process-emails`, `sync-sharepoint-list`, `obtener-disponibilidad-teams` y `obtener-disponibilidad-hoy` con `verify_jwt = false`, pero **no** registra `sync-holidays` ni `monitor-ticket-expirations`. Esto puede significar simplemente que se agregaron después sin actualizar el archivo de configuración local, lo cual no afecta el despliegue en la nube pero sí la experiencia de desarrollo local (`supabase functions serve`) y puede llevar a que su `verify_jwt` efectivo en producción sea el default de la plataforma (`true`), distinto del resto — conviene confirmar y homogeneizar.
- **`pruneMissingRows` con `syncPruneMissing=true` es potencialmente destructivo sin salvaguarda**: a diferencia de `sync-holidays` (que sí evita borrar si la API externa devuelve 0 filas), `sync-sharepoint-list` no tiene una protección equivalente explícita más allá de `if (!config.syncPruneMissing || sourceRows.length === 0) return 0` — es decir, si Graph devolviera una lista de SharePoint con **algunos** ítems pero por error de filtro/paginación devolviera muchos menos de los reales, `pruneMissingRows` borraría de Supabase todas las filas cuyo `syncTargetKey` no aparezca en ese subconjunto incompleto, sin ningún umbral de seguridad (por ejemplo, "no borrar si se eliminaría más del X% de las filas").
- **Sin reintentos ante fallos parciales de Graph o de los lotes de `upsert`/`delete`**: en ambas funciones, si Graph responde con error en una página intermedia de la paginación, o si un lote de `upsertRows`/`pruneMissingRows` falla, la función aborta por completo (excepción propagada hasta el `catch` global) dejando el estado a medio sincronizar, sin indicar qué lote específico falló ni permitir reanudar desde ahí.
- **Duplicación de lógica de autenticación Graph**: `getGraphAccessToken` en `sync-sharepoint-list/index.ts` es prácticamente idéntica a la de `monitor-ticket-expirations/graph.ts`, `process-emails/graph.ts` y las funciones `obtener-disponibilidad-*` — mismo patrón repetido cinco veces en el repositorio; principal candidato a extraer a un módulo compartido `supabase/functions/_shared/`.
- **Falta de logging estructurado de progreso**: ninguna de las dos funciones registra cuántas páginas de Graph se recorrieron, cuántos lotes de `upsert`/`delete` se ejecutaron, ni tiempos parciales — sólo hay un `console.error` final. Para operaciones de sincronización masiva (potencialmente miles de ítems de SharePoint), esto dificulta diagnosticar cuellos de botella o fallos a mitad de proceso.
- **Límite de tiempo de ejecución no considerado para listas grandes**: `fetchSharePointItems` recorre *todas* las páginas de la lista de SharePoint de forma secuencial antes de iniciar cualquier `upsert`; con listas muy grandes, esto podría acercarse al límite de tiempo de ejecución de las Edge Functions antes de escribir un solo registro en Supabase, perdiendo todo el trabajo de lectura ya realizado (no hay *streaming* de página → upsert incremental).
- **Sin pruebas automatizadas**: no se encontró cobertura de test para `mapItemToRow` (lógica de mapeo configurable con reglas especiales como `isSharePointIdField` y `shouldSetResolverActivoFalse`), ni para la validación exhaustiva de `readRequestBody`, pese a ser la función con más superficie de configuración dinámica del monorepo y, por tanto, la más propensa a errores de configuración en producción.
